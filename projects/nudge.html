CASE 01 / AU · CHURN

장기 백필에 맞는 계산 구조를 선택했습니다.

PROBLEM

범위 JOIN에서 발생한 fan-out

기존 BETWEEN 범위 JOIN은 과거 접속과 미래 재방문을 계산했습니다. 장기 백필 시 fan-out 문제를 확인했습니다.

DECISION

데이터 규모와 처리 조건에 맞는 구조

범위 JOIN을 UNIX_DATE + Window Function 기반 계산으로 바꾸기로 했습니다.

CASE 01 / IMPLEMENTATION

UNIX_DATE + Window Function으로 리팩터링했습니다.

과거 접속과 미래 재방문을 계산하는 AU / Churn 로직을 Window Function 기반으로 개선했습니다.

CASE 01 / VERIFICATION → RESULT

결과를 비교하고, 처리 비용을 확인했습니다.

VERIFICATION

기존 결과 40행을 셀 단위로 비교

변경 전후 결과를 비교해 mismatch 0을 확인했습니다. 처리 비용은 20일 백필을 기준으로 확인했습니다.

RESULT

결과 불일치 없이 처리 비용 감소

20일 백필 기준 slot_ms는 약 14배, shuffle은 약 7.8배 감소했습니다. 단순한 속도 개선보다 데이터 규모와 처리 조건에 맞는 구조로 개선한 경험입니다.

CASE 02 / SHORT-FORM COMMERCE

같은 주문 데이터도 산출 기준에 따라 판단이 달라집니다.

PROBLEM

노출부터 구매까지 연결되는 KPI

외부 API와 Commerce DB를 기반으로 clip exposure → purchase 전환 지표를 구성하고, 주문 단위 쿠폰을 상품별 KPI에 반영해야 했습니다.

DECISION

상품별 가격 비율로 쿠폰 배분

주문 단위 쿠폰을 상품별 가격 비율로 배분하는 산출 기준을 적용했습니다.

CASE 02 / IMPLEMENTATION

Raw 적재에서 분석용 mart까지 연결했습니다.

  1. 외부 API + Commerce DB
  2. GCSAPI raw 적재
  3. BigQuery / dbtMart

외부 API의 raw 데이터를 GCS에 저장하고, Commerce DB와 함께 BigQuery / dbt 기반 mart를 구성했습니다.

CASE 02 / VERIFICATION → RESULT

데이터 품질에 업무 맥락과 산출 기준을 포함했습니다.

VERIFICATION

검증 근거

검증 절차와 정량 지표는 추후 보완 예정입니다.

RESULT

Clip exposure → purchase 전환 지표 구성

동일한 주문 데이터도 쿠폰 배분 등 산출 기준에 따라 현업 판단이 달라질 수 있음을 경험했습니다. 데이터 품질은 값의 정확성뿐 아니라 업무 맥락과 산출 기준까지 포함한다고 생각합니다.
