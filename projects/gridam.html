A / CDC · 데이터 일관성

저장과 분석은 분리하되,
데이터의 기준은 하나로 맞췄습니다.

배경 / WHY · CONTEXT

일기 저장과 LLM 감정 분석의 분리

LLM 기반 감정 일기 서비스에서 일기 저장과 감정 분석을 분리했습니다. 분석을 별도로 처리하면서도 실제 저장 상태에 맞춰 후속 처리가 이어지도록 설계해야 했습니다.

문제 / PROBLEM

DB 저장과 이벤트 발행 사이의 간격

DB commit과 event publish는 별개로 수행됩니다. 저장은 성공했지만 이벤트 발행이 실패하면, 저장된 일기가 후속 분석으로 전달되지 않을 수 있다는 위험을 고려했습니다.

가설 / HYPOTHESIS

실제 commit된 변경을 후속 처리의 기준으로

애플리케이션의 이벤트 발행 대신 DB 변경 로그를 기준으로 삼으면, 저장 상태와 분석 흐름이 참조하는 기준을 하나로 맞출 수 있다고 봤습니다.

선택 / DECISION

MySQL을 Source of Truth로 두고 log-based CDC 선택

일기가 저장되는 MySQL을 기준 데이터로 설정했습니다. Binlog를 Debezium으로 수집하고 Kafka를 통해 분석으로 전달하는 구조를 선택해, DB 저장과 별도 이벤트 발행 시점의 불일치 문제를 피하고자 했습니다.

A / 구현 · IMPLEMENTATION

저장된 변경 사항을 분석 흐름에 전달했습니다.

  1. MySQL
  2. Binlog
  3. Debezium
  4. Kafka
  5. Python Consumer
  6. MongoDB

MySQL의 변경 로그를 Kafka로 전달하고, Python Consumer의 감정 분석 결과는 MongoDB로 이어지도록 구성했습니다. Schema Registry + Avro를 적용하고 MySQL / MongoDB / Redis의 역할을 분리했습니다.

A / 설계 결과 · RESULT · OPERATION

저장된 변경을 기준으로
후속 분석을 연결했습니다.

일기 저장 요청과 감정 분석 흐름을 분리하고, MySQL의 commit된 변경 로그를 후속 처리의 기준으로 삼았습니다. Schema Registry + Avro로 이벤트 스키마를 관리하는 구조를 구성했습니다.

B / 조회 성능 최적화 · PERFORMANCE OPTIMIZATION

인덱스·캐시 최적화로 개선했습니다.

문제 / PROBLEM

데이터 흐름 설계와 별도로, 조회 API의 응답 시간을 개선했습니다.

조치 / ACTION

조회 성능을 개선하기 위해 인덱스와 캐시를 최적화했습니다.
